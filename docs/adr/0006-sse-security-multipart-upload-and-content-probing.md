# 0006. HTTP SSE 访问控制、透明分段上传与纯文本深度探测

## 背景与决策 (Context & Decision)

随着服务在云原生容器与跨网络多智能体集群中常驻运行，且面对海量异构非标数据集，系统呈现出以下三个关键演进诉求：
1. **远程调用安全与跨域互联**：HTTP SSE 常驻微服务在缺乏反向代理时面临未授权调用风险，且浏览器 Web 客户端面临 CORS 跨域拦截；
2. **大对象传输韧性**：针对数百 MB 甚至数 GB 的大型文件，单流 `PutObject` 无法突破 5GB 协议硬限制，且中途网络波动会导致整包重传失败；
3. **内容检视误伤问题**：许多自建 S3 兼容服务中存储的纯文本、日志或无后缀配置文件被统一标记为 `application/octet-stream`，单纯依赖 MIME 拦截会导致 Agent 无法阅读合法的纯文本内容。

我们决定采纳以下核心架构决策：
1. **SSE 传输层 Bearer Token 鉴权与全量 CORS**：
   - 引入 `MCP_S3_API_KEY` 可选配置；配置后对 `/sse` 与 `/message` 强制校验 `Authorization: Bearer <token>`（兼容 URL 查询参数 `?token=`）；
   - 内置标准 CORS 响应头并支持 `OPTIONS` 预检拦截，彻底解除 Web 客户端访问阻碍；
2. **本地文件流上传透明升级为 Multipart Upload**：
   - 引入 `@aws-sdk/lib-storage` 的 `Upload` 管理器，对外保持统一工具契约；
   - 设定分段阈值（大文件自动启用分段上传，并发分片与自动重试），彻底消除容量上限与网络脆弱性；
3. **512 字节 Null Byte 深度内容探测**：
   - 当对象 MIME 为 `application/octet-stream` 且缺少已知文本扩展名时，探测前 512 字节；
   - 采用零容忍 Null Byte (`\0`) 算法判定：若存在空字节立即拦截并引导使用外链；若无空字节且为有效 UTF-8，则安全放行直读。

## 权衡考量 (Considered Options)

- **SSE 安全方案**：
  - 仅依赖基础设施反向代理：在轻量容器或独立常驻测试环境下缺乏内建防线；
  - 内建可选 Bearer Token 与 CORS（已采纳）：未配置时保持零门槛内网直连，配置后一键升级为生产安全防线。
- **大对象上传方案**：
  - 新增专用工具 `upload_large_file`：增加了上层 AI Agent 的认知负荷与调度决策复杂度；
  - `upload_file` 内部透明自适应（已采纳）：对模型保持统一心智模型，由底层根据数据量自动决策上传拓扑。
- **文本检测方案**：
  - 纯 MIME 白名单：大量缺少 Content-Type 的日志和配置文件被误伤阻断；
  - 启发式 Magic Bytes 零容忍探测（已采纳）：兼具极低开销（仅读前 512B）与 0 误判率（遵循 Git 原生文本探测规范）。

## 后果与影响 (Consequences)

- 优势：
  - 支持多终端 WebUI 安全直连常驻容器；
  - 彻底解除了大文件单流传输失败的痛点；
  - 大幅提升了 AI Agent 自主探索未知数据集时的文本读取宽容度与真实健壮性。
- 代价：
  - 需引入 `@aws-sdk/lib-storage` 生产依赖；
  - 文本直读逻辑增加了前置 512 字节条件探测的分支。
